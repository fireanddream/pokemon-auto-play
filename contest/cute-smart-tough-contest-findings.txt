TEST SCOPE AND SETTINGS
Cute, Smart, and Tough each run Normal -> Super -> Hyper -> Master five times.
Each category has 20 contests, six responses per contest, and 450 opportunities:
Normal has three inputs per response; the other ranks have four.
The live debug runner presses buttons and records feedback for every executed input.
Current defaults: fixed category/rank profiles; -7-emulator-frame input offset;
2 held / 10 released emulator frames; initial feedback at press +11 frames.
Execution is uncapped, with no overlay host wait or entry speed calibration.
Run timers are enabled: 7,200 total / 300 per-stage host seconds for each category.
Optional midpoint diagnostics are disabled; normal counted corrections and the
no-forward-progress skip policy apply. No per-run timing overrides were supplied.
Each category owns one post-load baseline and reloads it after every contest,
including its final contest. Native slot 0 (API slot 10) is temporary transport.
Midpoints use fresh paused zero-frame images. Accepted line: x=128 or x=129;
exact first pixel: x=128. Signed pixel errors are relative to x=128, with negative
values early/left. Pixel-derived frame errors below are fixed-speed estimates,
not measured pointer crossing frames or measured button timing errors.

INTERPRETATION
The requested default comparisons are complete. Cute had no misses or skips;
Smart's eight Good results were all fourth high-rank inputs with the same early
pre-input pixel pattern. Tough had no executed timing misses and four cue skips.
Counted midpoint correction reached the accepted line in every early attempt.
Accepted midpoint pixels alone did not guarantee Excellent feedback or complete
cue evidence: the Smart Good results and Tough skips all had midpoint x=128.

Smart required adjustments on 88/120 responses (73.3%), including 58/60
Hyper/Master responses (96.7%). Correction refreshes the position/time anchor
but retains the selected fixed speed. The eight missed fourth inputs lagged their
fresh midpoint-based predictions. Working hypothesis: Smart's Hyper/Master rate of
71/120 pixel per emulator frame may be too high. Overestimated speed shortens
calculated waits, allowing prediction to get ahead again before later inputs.
The deliberate x=127 capture target explains many small corrections, so adjustment
frequency alone does not establish a speed error. Frame/pixel phase and rounding
remain possible contributors; no replacement rate is verified.

Exact crossing frames, game timing thresholds, and the cause of Smart's fixed-model
pixel disagreement remain unresolved. These repetitions reused one baseline per
category; they do not establish behavior for other prepared saves.

The retained Beauty report covers 40 contests/900 presses: 895 Excellent, five Good.
It used ten loops, midpoint diagnostic continuation, and disabled run timers;
the current comparisons used five loops and default midpoint/timeout behavior.
Those differences limit category-only causal conclusions from the older results.
Shared timing/reader changes and the startup handoff issue remain separate follow-ups.
